# Research: Cross-platform mobile+web tech stack for Mixtape Party

Ticket: [#5 "Research: cross-platform mobile+web tech stack options"](https://github.com/jamiwardlow/mixtape-party/issues/5), child of [#1](https://github.com/jamiwardlow/mixtape-party/issues/1).

## Question

Mixtape Party needs one codebase (or tightly-shared codebases) spanning web + iOS + Android that embed three third-party music SDKs:
- Spotify Web Playback SDK
- Apple MusicKit (JS on web, native on iOS; Android situation below)
- YouTube IFrame Player API

## The load-bearing fact that shapes every option

**The Spotify Web Playback SDK does not work reliably inside an embedded/native-app WebView, even though it "supports" mobile browsers.** This one fact eliminates "just WebView the web app on mobile" as a clean answer for Spotify, for every framework below.

- Spotify's own docs say the SDK is "supported by most web browsers (Chrome, Firefox, Safari and Microsoft Edge) in both mobile (Android and iOS) and Desktop," but the same page notes it requires `encrypted-media` and `autoplay` to be allowed on iframes, which Chrome's Feature Policy disallows by default for cross-origin iframes — a real complication for anything embedding it. — [Web Playback SDK docs](https://developer.spotify.com/documentation/web-playback-sdk)
- Playback relies on EME/DRM key systems, and Android/iOS **app WebViews frequently don't expose a usable EME key system**, even when `navigator.requestMediaKeySystemAccess()` exists. Filed and confirmed against `react-native-webview`: [EME / DRM keysystems are not supported · Issue #2271](https://github.com/react-native-webview/react-native-webview/issues/2271).
- Developers who tried this in Flutter's `webview_flutter` hit the same wall from the other side: "On iOS, the song will play for 10 seconds and then stop. On Android, the song will not play at all" when hosting the Web Playback SDK inside a Flutter WebView — reported on the [Spotify Community: Web Playback SDK Does Not Work In Flutter App Running On iOS](https://community.spotify.com/t5/Spotify-for-Developers/Web-Playback-SDK-Does-Not-Work-In-Flutter-App-Running-On-iOS-and/td-p/5887838).
- Native mobile browser support itself was absent for years and only partially improved: original ask in [spotify/web-playback-sdk#10 "Why aren't mobile browsers supported?"](https://github.com/spotify/web-playback-sdk/issues/10) (opened 2018) got no follow-through per the requester in [spotify/web-playback-sdk#72](https://github.com/spotify/web-playback-sdk/issues/72), who says a maintainer promised mobile support "over a year prior" with no update since. The repo is now archived (June 2020) — Spotify is not actively evolving this SDK's browser story.
- The vendor-sanctioned path for real mobile apps is a **different SDK entirely**: the native **Spotify App Remote SDK** (iOS/Android), not the Web Playback SDK. It requires the Spotify app to be installed on-device and controls that app rather than streaming audio directly in-process.

Implication: any stack that wants Spotify playback on iOS/Android needs a native bridge to the App Remote SDK regardless of what's used for web. WebView-only approaches do not give you Spotify audio on mobile.

## MusicKit (Apple Music)

- **Web**: MusicKit JS is the only web option, script-tag loaded from Apple's CDN. It works in real browsers including mobile Safari, but **inside an app WebView it needs explicit "Native WebView" handling** — MusicKit JS v3 ships a documented Native WebView authorization flow because, without it, `authorize()` tries to open a real browser window instead of behaving like an in-app auth flow. Developers hit this directly: [MusicKit JS Native WebView Authorization Flow Not Initiating](https://developer.apple.com/forums/thread/746776) (Apple Developer Forums) and related 403-on-authorize reports in [MusicKit web 403 error when authorizing](https://developer.apple.com/forums/thread/747653).
- **iOS native**: Apple's `MusicKit` Swift framework is first-party, current, and the recommended path for a native iOS app — full parity, actively maintained, documented at [Apple Developer: MusicKit](https://developer.apple.com/musickit/).
- **Android**: Apple ships a MusicKit SDK for Android, but it is **stale and feature-incomplete**. Developers report it "has not been updated for years" and lacks docs beyond generated Javadoc, per discussion on [Apple Developer Forums: MusicKit SDK for Android update?](https://developer.apple.com/forums/thread/734577), and specific gaps like missing radio-station playback are noted in [MusicKit for Android does not support to play radio station yet?](https://developer.apple.com/forums/thread/660041). Overview page: [Apple Music - Android MusicKit](https://developer.apple.com/musickit/android/).
- No cross-platform (React Native / Flutter) first-party wrapper exists from Apple. Community wrappers exist (e.g. [`@lomray/react-native-apple-music`](https://github.com/Lomray-Software/react-native-apple-music)) but are third-party and unofficial, wrapping the same aging native SDKs.

Implication: MusicKit is solid on web and iOS; Android is the weak link industry-wide, independent of the app framework chosen.

## YouTube IFrame Player API

- Officially a **web-only, iframe-based** API: [IFrame Player API reference](https://developers.google.com/youtube/iframe_api_reference). There is no first-party native SDK equivalent for playback-in-app beyond wrapping the iframe in a WebView, which is exactly what every mobile wrapper (React Native, Flutter) does under the hood.
- **Background-audio is explicitly against YouTube's terms**: "Background playback behavior is against YouTube terms of service... you won't be able to publish your app on the Play Store" if you enable it — documented via the developer-policy pages ([Developer Policies](https://developers.google.com/youtube/terms/developer-policies), [Required Minimum Functionality](https://developers.google.com/youtube/terms/required-minimum-functionality)) and confirmed by real developer fallout: a maintainer/user reports their app was **taken down from the Play Store for a "Device and Network Abuse policy" violation** after enabling background play, in [react-native-youtube-iframe#72 "Background play"](https://github.com/LonelyCpp/react-native-youtube-iframe/issues/72).
- React Native: [`react-native-youtube-iframe`](https://github.com/LonelyCpp/react-native-youtube-iframe) wraps the IFrame API in `react-native-webview`; actively used, but see the ToS caveat above and platform rendering bugs like [Video not visible on Android #26](https://github.com/LonelyCpp/react-native-youtube-iframe/issues/26).
- Flutter: `youtube_player_iframe`/`youtube_player_flutter` similarly wrap the IFrame API inside `webview_flutter`, inheriting whatever WebView bugs Flutter's own WebView plugin has, e.g. [iOS 17.1+ auto-muting embedded YouTube videos, flutter/flutter#139193](https://github.com/flutter/flutter/issues/139193), [autoplay broken on webview_flutter 4.0.1, flutter/flutter#118483](https://github.com/flutter/flutter/issues/118483), and [exiting fullscreen pauses the iframe on iOS, flutter/flutter#144974](https://github.com/flutter/flutter/issues/144974).

Implication: YouTube is "fine" everywhere in the sense that it's always a WebView-hosted iframe no matter the framework — but background play, a likely desired feature for a party mixtape app, is a ToS violation that can get an app pulled from the Play Store, and this is independent of framework choice.

## Option comparison

### 1. React Native + React Native Web (or Expo)

- **Spotify**: No documented working path for the Web Playback SDK inside `react-native-webview` (EME/DRM broken — [react-native-webview#2271](https://github.com/react-native-webview/react-native-webview/issues/2271)). Real mobile playback requires bridging to the native App Remote SDK; community wrappers exist ([`react-native-spotify-remote`](https://github.com/cjam/react-native-spotify-remote), [`@wwdrew/expo-spotify-sdk`](https://www.npmjs.com/package/@wwdrew/expo-spotify-sdk)) but `react-native-spotify-remote`'s last release was ~4 years ago per npm, i.e. low-maintenance-confidence. On React Native Web (real browser DOM), the Web Playback SDK works directly like any web app since RNW renders to actual DOM/web APIs.
- **MusicKit**: Web via MusicKit JS works directly under React Native Web (real browser). Native iOS needs a bridge to Apple's Swift MusicKit framework (community wrapper: [`expo-music-kit`](https://github.com/0xA-10/expo-music-kit)). Android inherits Apple's own stale Android SDK problem.
- **YouTube**: `react-native-youtube-iframe` is mature and widely used; on RNW/web, the IFrame API just runs natively in the DOM.
- **Maturity**: React Native itself and Expo are highly mature, large ecosystems. React Native Web is officially documented and Expo has "first-class support for building full-stack websites with React" ([Expo: Develop websites with Expo](https://docs.expo.dev/workflow/web/)), but true code sharing is capped by the need for platform-specific native modules for Spotify App Remote and MusicKit-native — these are not shared code, they're per-platform bridges.
- **Dealbreakers reported**: EME/DRM absence in WebView ([react-native-webview#2271](https://github.com/react-native-webview/react-native-webview/issues/2271)); aging/unmaintained Spotify remote wrapper; Play Store takedown risk for YouTube background play ([react-native-youtube-iframe#72](https://github.com/LonelyCpp/react-native-youtube-iframe/issues/72)).

### 2. Flutter

- **Spotify**: Same EME/DRM WebView failure as above, directly reported for `webview_flutter` on the [Spotify Community](https://community.spotify.com/t5/Spotify-for-Developers/Web-Playback-SDK-Does-Not-Work-In-Flutter-App-Running-On-iOS-and/td-p/5887838): 10s cutoff on iOS, no playback at all on Android. Flutter has a community `spotify_sdk` package ([pub.dev](https://pub.dev/packages/spotify_sdk), [GitHub](https://github.com/brim-borium/spotify_sdk)) that wraps the native App Remote SDKs directly (bypassing WebView) for mobile, plus Web Playback SDK support for Flutter Web specifically — this is the credible path, not the WebView route.
- **MusicKit**: No first-party Flutter package from Apple; would need a custom platform channel to the native Swift `MusicKit` framework on iOS, and to Apple's stale Android SDK on Android. Web would use MusicKit JS inside `webview_flutter` for a Flutter Web build, or a plain web frontend if Flutter Web is skipped for the music surface.
- **YouTube**: `youtube_player_iframe`/`youtube_player_flutter` wrap the IFrame API in `webview_flutter`; functional but inherits WebView plugin bugs (auto-mute on iOS 17.1+, autoplay regressions, fullscreen-pause) cited above.
- **Maturity**: Flutter's mobile story is very mature; **Flutter Web is comparatively weaker for a content/SEO-relevant marketing shell** — official-adjacent analysis notes Flutter Web's canvas-based rendering doesn't produce a real DOM, which hurts SEO for anything that needs to be crawlable (landing pages, party invite links, etc.) — see the WebView plugin/rendering discussion referenced from [flutter/flutter#183992](https://github.com/flutter/flutter/issues/183992) and general Flutter Web SEO limitations. For a music-embed use case specifically, Flutter's WebView plugin is still consolidating: "The Flutter Team is working closely to integrate Community Plugin features in the Official WebView Plugin" per the plugin's own documentation, meaning API stability on this exact path is still an open concern.
- **Dealbreakers reported**: Web Playback SDK unusable via WebView on mobile ([Spotify Community thread](https://community.spotify.com/t5/Spotify-for-Developers/Web-Playback-SDK-Does-Not-Work-In-Flutter-App-Running-On-iOS-and/td-p/5887838)); YouTube auto-mute/autoplay/fullscreen WebView bugs on iOS ([flutter/flutter#139193](https://github.com/flutter/flutter/issues/139193), [#118483](https://github.com/flutter/flutter/issues/118483), [#144974](https://github.com/flutter/flutter/issues/144974)); weak SEO/DOM output for Flutter Web if any part of the product needs to be indexable or link-shareable with rich previews.

### 3. Separate native apps (Swift/Kotlin) + a shared web app + shared backend

- **Spotify**: Cleanest fit for mobile — native iOS/Android apps talk to the real Spotify App Remote SDK / iOS SDK directly, no WebView DRM problem at all. Web app uses the Web Playback SDK directly in a real browser (its native, documented environment) — this is the SDK's actual intended target per [Spotify's own docs](https://developer.spotify.com/documentation/web-playback-sdk).
- **MusicKit**: Cleanest fit — native iOS app uses Apple's current, first-party `MusicKit` Swift framework with full feature parity; web app uses MusicKit JS directly in-browser, its intended environment, with no WebView authorize() workaround needed. Android still hits Apple's stale MusicKit-for-Android SDK regardless of framework choice — this is an Apple-side limitation, not a framework limitation.
- **YouTube**: Web app embeds the IFrame API directly (as designed). Native apps use IFrame-in-WebView (same as RN/Flutter) or Android's own [`android-youtube-player`](https://github.com/PierfrancescoSoffritti/android-youtube-player) library, or the native YouTube iOS player helper — still bound by the same ToS restriction on background play.
- **Maturity**: Each surface uses the SDK in the environment it was actually built and documented for, so this option has the fewest "fighting the platform" issues and the fewest exotic bridge dependencies. The cost is zero UI code sharing between the three targets and 3x the surface area to build/maintain — a real velocity and consistency tax, especially for a small team.
- **Dealbreakers**: none specific to the SDKs (that's the point of this option) — the dealbreaker is organizational/cost: three codebases, three release pipelines, and UI/UX drift risk without shared design-system discipline.

## Bottom line

- None of the three SDKs work cleanly through a generic mobile WebView; each requires either a native bridge (Spotify App Remote, MusicKit native) or acceptance of a real product constraint (YouTube background play banned by ToS).
- React Native and Flutter both reduce this problem to "how do I write a per-platform native bridge for Spotify and MusicKit," which is unavoidable regardless of framework — the frameworks mainly change how much *other* UI code can be shared, not whether the music SDKs need native bridging.
- Flutter's web output is the biggest additional risk if any part of the product (marketing pages, shareable mixtape links) needs to be crawlable/shareable with normal link previews, since Flutter Web doesn't produce a real DOM.
- React Native + React Native Web/Expo shares more idiomatic web code with the mobile app (same JS/React model, real DOM on web) and has a larger, more current set of community bridges for Spotify App Remote and MusicKit, though those bridges are third-party and vary in maintenance freshness (flagged above).
- The separate-native + shared-web option sidesteps every SDK-embedding problem identified here by using each SDK in its officially intended environment, at the cost of no shared mobile/web UI code — worth it only if the team has bandwidth for three native surfaces or if the SDK friction above proves too costly to work around in RN/Flutter.
