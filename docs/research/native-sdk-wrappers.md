# Research: currently-maintained Spotify App Remote + MusicKit-iOS RN/Expo wrapper packages

Ticket: [#38 "Research: currently-maintained Spotify App Remote + MusicKit-iOS RN/Expo wrapper packages"](https://github.com/jamiwardlow/mixtape-party/issues/38), child of [#32 "Mixtape Party: deploy & test-loop plan"](https://github.com/jamiwardlow/mixtape-party/issues/32).

## Question

[#5's research](https://github.com/jamiwardlow/mixtape-party/blob/research/tech-stack/docs/research/tech-stack.md) established that real mobile playback needs native bridges — Spotify's **App Remote SDK** (not Web Playback SDK) and Apple's native **MusicKit-iOS** framework (not MusicKit JS) — but only noted that "community RN bridges exist, of varying maintenance freshness," without naming packages. This app is Expo SDK ~57, Expo Router, **managed workflow** (`mobile/app.json` `plugins`: `expo-router`, `expo-status-bar`, `expo-secure-store`, `expo-web-browser`, `expo-splash-screen` — no bare-workflow escape hatch in use today). This doc names current candidates, checked against npm registry data and GitHub repo activity (not README self-description), and evaluates each for Expo config-plugin / `expo prebuild` compatibility.

## Spotify App Remote SDK wrappers

### `@wwdrew/expo-spotify-sdk` — recommended

- **npm**: latest `2.3.2`, published **2026-07-22** (registry `time` field), first published 2024-01-12 — [`npm view` via registry.npmjs.org](https://www.npmjs.com/package/@wwdrew/expo-spotify-sdk). Version history (`1.0.0` → `2.3.2`) shows a steady cadence, not a one-off dump.
- **GitHub**: [`wwdrew/expo-spotify-sdk`](https://github.com/wwdrew/expo-spotify-sdk) — not archived, not disabled, `pushed_at` **2026-07-22**, 17 stars, **0 open issues** (all recent issues — [#74](https://github.com/wwdrew/expo-spotify-sdk/issues/74), [#72](https://github.com/wwdrew/expo-spotify-sdk/issues/72), [#67](https://github.com/wwdrew/expo-spotify-sdk/issues/67) — closed with a fix + release commit, per [CHANGELOG.md](https://github.com/wwdrew/expo-spotify-sdk/blob/main/CHANGELOG.md)). CI badge and a `release-please`-style changelog indicate a working release pipeline, not just a personal snapshot.
- **Expo integration**: this is an [Expo Module](https://docs.expo.dev/modules/overview/) (not a bare RN native module retrofitted), ships a **first-party typed config plugin** at `@wwdrew/expo-spotify-sdk/plugin`, and its own README quick start is `npx expo install` → add plugin to `app.config.ts` → `npx expo prebuild` — i.e. built for CNG/managed workflow from the start, per [the README](https://github.com/wwdrew/expo-spotify-sdk/blob/main/README.md).
- **Versioning tracks Expo SDK lane**: `1.x` = Expo SDK 55 (iOS 15.1 floor), `2.x` = Expo SDK 56+ (iOS 16.4 floor) — see [ADR-0005](https://github.com/wwdrew/expo-spotify-sdk/blob/main/docs/adr/0005-sdk-lane-versioning.md). This app is on Expo `~57.0.20`, so the `2.x`/`main` lane applies directly.
- **What it wraps**: Spotify's [iOS SDK v5.0.1](https://github.com/spotify/ios-sdk) and [Android SDK v4.0.1](https://github.com/spotify/android-sdk) — Auth + App Remote + Player/User/Content/Images namespaces, i.e. the actual native App Remote SDK, not a webview shim.
- **Native distribution**: iOS pulls `SpotifyiOS` via a CocoaPods HTTP binary pod, injected into the Podfile by the config plugin at `pod install` time ([ADR-0009](https://github.com/wwdrew/expo-spotify-sdk/blob/main/docs/guides/native-sdk-distribution.md)); Android pulls the App Remote AAR from Spotify's GitHub at Gradle build time and the Auth SDK from Maven Central. Neither requires vendoring binaries into this repo.

### Abandoned: `cjam/react-native-spotify-remote` and its forks

- **npm** `react-native-spotify-remote`: latest `0.3.10`, published **2021-07-15**, registry `modified` **2022-06-17** — no publish in ~4-5 years.
- **GitHub**: [`cjam/react-native-spotify-remote`](https://github.com/cjam/react-native-spotify-remote) is not archived and shows `pushed_at` **2025-11-16** with **77 open issues**, but the actual commit log shows only a `README.md` edit in Jan 2025 and one real fix in Feb 2024 — the repo is not dead, but it is not shipping npm releases, and 77 open issues with no recent code fixes is a real maintenance backlog, not "actively maintained."
- Scoped forks exist — [`@fkeulen/react-native-spotify-remote`](https://www.npmjs.com/package/@fkeulen/react-native-spotify-remote) (`0.3.11-5`, ~3 years old per npm), [`@hoangvvo/react-native-spotify-remote`](https://www.npmjs.com/package/@hoangvvo/react-native-spotify-remote), [`@listty/react-native-spotify-remote`](https://www.npmjs.com/package/@listty/react-native-spotify-remote) — these are individual maintainers' unofficial republishes to unblock themselves, not a maintained upstream, and **none ship an Expo config plugin**; this whole lineage is a bare-RN-era native module (manual `pod install` + manual Android Gradle/manifest edits), so on Expo managed workflow it would need a custom local config plugin written from scratch, with no upstream guidance.
- **Verdict**: confirms and sharpens #5's "varying maintenance freshness" finding — this is the stale end of that range. Not recommended.

## Apple MusicKit-iOS wrappers

### `@lomray/react-native-apple-music` — recommended, with a real Expo/EAS gotcha

- **npm**: latest `1.4.0`, published **2026-04-07** (registry `time` field), first published 2024-01-05 — [`@lomray/react-native-apple-music`](https://www.npmjs.com/package/@lomray/react-native-apple-music). Ten published versions, steady cadence.
- **GitHub**: [`Lomray-Software/react-native-apple-music`](https://github.com/Lomray-Software/react-native-apple-music) — not archived, `pushed_at` **2026-04-07**, 34 stars, 4 open issues.
- **What it wraps**: Apple's native `MusicKit` Swift framework — real playback control (`play`, `pause`, `skipToNextEntry`, `skipToPreviousEntry`, `seekToTime`, `configurePlayer`), catalog search, library songs/playlists, auth + subscription checks — per the [README feature table](https://github.com/Lomray-Software/react-native-apple-music/blob/prod/README.md). This is the fullest-featured MusicKit wrapper found; **iOS only, no Android** (Apple's own MusicKit-for-Android SDK is the stale one #5 already flagged, and this package doesn't attempt to bridge it).
- **Expo integration — no shipped config plugin yet.** As of this research there is an **open, unmerged PR** — [wwdrew's PR #16, "feat: add Expo config plugin for NSAppleMusicUsageDescription"](https://github.com/Lomray-Software/react-native-apple-music/pull/16) — filed in response to [issue #16](https://github.com/Lomray-Software/react-native-apple-music/issues/16), still `open`/`merged: false`. Today, integrating this package on Expo managed workflow means writing a small local config plugin yourself (e.g. `withInfoPlist` to inject `NSAppleMusicUsageDescription`, `withEntitlementsPlist` to add the MusicKit entitlement) rather than installing one from the package — auto-linking otherwise "just works" for iOS (`react-native > 0.61`) per the README, and prebuild will not wipe a locally-authored config plugin's output the way it would wipe hand-edited Podfile/Xcode-project changes.
- **A real, currently-unresolved EAS Build gotcha**: [issue #14, "MusicKit entitlement incompatible with EAS Build (Expo) — guidance needed"](https://github.com/Lomray-Software/react-native-apple-music/issues/14) documents that declaring `com.apple.developer.musickit` causes EAS Build (and local Xcode automatic signing) to fail with *"Provisioning profile does not include the com.apple.developer.musickit entitlement."* Apple treats MusicKit as an **App Service, not a standard capability** — every attempt logged in the issue (manually creating a profile in the portal, `credentialsSource: "remote"` vs `"local"` in `eas.json`, clearing/recreating certs) failed the same way, and the maintainer's only reply (as of this writing) is "we haven't yet validated a working EAS Build setup ... we're planning to look into this." **Independently confirmed as a broader pattern**, not specific to this package: Expo's own [iOS capabilities doc](https://docs.expo.dev/build-reference/ios-capabilities/) states *"EAS Build will only enable capabilities that it has built-in support for, any unsupported entitlements must be manually enabled via Apple Developer Console"* — MusicKit is not in EAS Build's supported-capabilities list, so this isn't a bug in the package, it's a gap in EAS Build's automatic capability sync that every MusicKit-on-Expo project hits. Mitigation available today: enable the MusicKit App Service on the App ID in the Apple Developer portal by hand, then keep provisioning-profile regeneration on `credentialsSource: "local"` so EAS doesn't blow away a manually-provisioned profile — but there is no confirmed, documented, fully-working recipe yet per the linked thread.
- **Also flagged**: [issue #13](https://github.com/Lomray-Software/react-native-apple-music/issues/13) reports a new `postinstall` script appearing in `1.3.0` as a "potential Security Alert" — worth a quick look at the postinstall script's contents before pinning a version, though it's an open report, not a confirmed compromise.

### Ships a config plugin, but too thin to rely on: `@beatsphere/expo-apple-music-kit`

- **npm**: only one version ever published, `0.1.0`, on **2026-04-23** — [registry data](https://registry.npmjs.org/@beatsphere/expo-apple-music-kit).
- **GitHub**: [`Beatsphere/expo-apple-music-kit`](https://github.com/Beatsphere/expo-apple-music-kit) — **one commit total** ("initial release ... v0.1.0"), 0 stars, 1 open issue (a broken Android Gradle/Kotlin-plugin conflict filed 2026-09-05, days before this research).
- It does ship a real Expo config plugin (auto-configures `Info.plist` + `AndroidManifest.xml`, documented `npx expo prebuild --clean` flow) — the integration story is the best of any candidate here.
- **But it has no playback control at all.** Its API surface is auth (`requestAuthorization`, `getUserToken`), read-only `getPlaybackState()` (iOS 16+ only, via `SystemMusicPlayer` — reports whatever the OS-level Apple Music app happens to be playing, doesn't let this app start/stop/queue anything), and REST helpers (`searchCatalog`, `getRecentlyPlayedTracks`, `getHeavyRotation`). There is no `play()`/`pause()`/`skip()` — it cannot drive playback of a mixtape, only observe system Apple-Music state and hit the read-side REST API. Combined with a single-commit history and zero adoption, this is not viable as the primary package today; worth re-checking in a few months if it grows a playback API and a track record.

## Required permissions / entitlements summary

| | Spotify (`@wwdrew/expo-spotify-sdk`) | Apple Music (`@lomray/react-native-apple-music`) |
|---|---|---|
| External registration | App must be registered in the [Spotify Developer Dashboard](https://developer.spotify.com/dashboard) with a redirect URI matching `{scheme}://{host}` exactly | App ID needs the **MusicKit App Service** enabled in the Apple Developer portal; requires a paid Apple Developer Program membership/team |
| iOS config | URL scheme registered under Info → URL Types (plugin does this on `prebuild`) | `NSAppleMusicUsageDescription` in `Info.plist`; `com.apple.developer.musickit` in `.entitlements` (no shipped plugin — write a local `withInfoPlist`/`withEntitlementsPlist` plugin) |
| Android config | Gradle `manifestPlaceholders` for `spotifyClientId`/`spotifyRedirectUri`/etc., plus `com.spotify.android:auth` and OkHttp deps in `build.gradle`; no manual `AndroidManifest.xml` edits needed (module's own manifest merges in `<queries>` for package visibility) | N/A — package is iOS-only |
| Runtime dependency | The Spotify app must be installed on-device for App Remote to control it (this is inherent to App Remote, not a package limitation, per [#5](https://github.com/jamiwardlow/mixtape-party/blob/research/tech-stack/docs/research/tech-stack.md)) | Apple Music subscription for playback; MusicKit APIs gated behind user authorization dialog |
| Known Expo/EAS gotcha | None found | EAS Build / Xcode automatic signing currently **fails to provision** the MusicKit entitlement automatically — [issue #14](https://github.com/Lomray-Software/react-native-apple-music/issues/14), confirmed as a general EAS Build capability-sync gap by [Expo's own docs](https://docs.expo.dev/build-reference/ios-capabilities/) |

## Prebuild / managed-workflow compatibility summary

| Package | Config plugin | Prebuild-safe | Manual native edits needed |
|---|---|---|---|
| `@wwdrew/expo-spotify-sdk` | Yes, shipped, typed | Yes — this is its designed workflow | None; plugin injects Podfile line + Gradle manifest placeholders on every `prebuild` |
| `cjam/react-native-spotify-remote` (+ forks) | No | Not attempted/documented | Manual `pod install`, manual Android Gradle + manifest edits — prebuild regeneration would wipe any hand edits to `ios/`/`android/` unless re-expressed as a custom config plugin |
| `@lomray/react-native-apple-music` | No (PR [#16](https://github.com/Lomray-Software/react-native-apple-music/pull/16) open, unmerged) | Yes, if you write a ~20-line local config plugin (`withInfoPlist` + `withEntitlementsPlist`) — auto-linking otherwise needs no manual Xcode project edits | Write your own local plugin for Info.plist + entitlements; separately solve the EAS Build entitlement-provisioning gap above (portal-side, not code-side) |
| `@beatsphere/expo-apple-music-kit` | Yes, shipped | Yes | None for what it does — but what it does is auth/read-state/search only, not playback |

## Recommendation

- **Spotify: [`@wwdrew/expo-spotify-sdk`](https://www.npmjs.com/package/@wwdrew/expo-spotify-sdk)**, version `2.x` (matches Expo SDK 56+, this app is `~57`). Integration: `npx expo install @wwdrew/expo-spotify-sdk`, add `withSpotifySdk` from `@wwdrew/expo-spotify-sdk/plugin` to `mobile/app.json`'s `plugins` array with `clientID`/`scheme`/`host`, run `npx expo prebuild`. Register the app + redirect URI in the Spotify Developer Dashboard first. This is a clean fit for the existing managed workflow — no bare-workflow ejection needed.
- **Apple Music: [`@lomray/react-native-apple-music`](https://www.npmjs.com/package/@lomray/react-native-apple-music)** for actual playback control (the only maintained candidate that can `play`/`pause`/`skip`/`seek`, not just read state). It **requires prebuild + a small hand-written local config plugin** (no shipped plugin yet — track [PR #16](https://github.com/Lomray-Software/react-native-apple-music/pull/16) for when one merges) to inject `NSAppleMusicUsageDescription` and the `com.apple.developer.musickit` entitlement. Before committing engineering time here, budget for the **unresolved EAS Build MusicKit-entitlement provisioning gap** (issue #14 above) — this needs to be spiked against this project's actual EAS Build setup early, since it's an Apple/EAS capability-sync limitation, not something the package or a config plugin can paper over. If that spike fails to find a workaround, the fallback is local (non-EAS) Xcode builds signed manually for the MusicKit-dependent build, which is a real process cost for an Expo-managed-workflow team.
- Re-check `@beatsphere/expo-apple-music-kit` in a few months — it has the nicest Expo integration story (shipped config plugin, both platforms) but is a week-old single-commit project with no playback API today, not usable as-is.
